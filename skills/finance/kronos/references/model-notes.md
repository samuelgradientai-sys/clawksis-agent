# Kronos model notes

Kronos (Shi et al., *Kronos: A Foundation Model for the Language of Financial Markets*,
arXiv 2508.02739, AAAI 2026) is a decoder-only Transformer over tokenized OHLCV candles,
pretrained on 12B+ K-line records from 45 exchanges. Code: `shiyu-coder/Kronos` (MIT).
Weights: Hugging Face org `NeoQuasar` (labelled MIT; the repos carry no separate LICENSE
file). The skill downloads both at setup time and never vendors them.

## Model zoo

| `--model` | Weights | Tokenizer | Context | Params | Revision pin |
|---|---|---|---|---|---|
| `mini` | `NeoQuasar/Kronos-mini` | `NeoQuasar/Kronos-Tokenizer-2k` | 2048 | 4.1M | none yet: `--pin-on-first-use` |
| `small` (default) | `NeoQuasar/Kronos-small` | `NeoQuasar/Kronos-Tokenizer-base` | 512 | 24.7M | `901c26c1…` / tokenizer `0e011738…` |
| `base` | `NeoQuasar/Kronos-base` | `NeoQuasar/Kronos-Tokenizer-base` | 512 | 102.3M | none yet: `--pin-on-first-use` |

`Kronos-large` (499M) is not public. The small/tokenizer-base revisions are the ones upstream's
own regression test pins (`tests/test_kronos_regression.py` at the pinned commit). Only
`config.json` and `*.safetensors` are downloaded; a repo without safetensors fails closed
instead of falling back to pickled `.bin` weights.

## Upstream code pin

`kronos_setup.py` fetches `codeload.github.com/shiyu-coder/Kronos/tar.gz/<UPSTREAM_SHA>` and
keeps only `model/__init__.py`, `model/kronos.py`, `model/module.py` and `LICENSE`, read from
the archive in memory. Each file must match the sha256 recorded in `UPSTREAM_FILES`
(`scripts/_kronos_common.py`), computed from the git blobs at the pinned commit, so a
re-compressed GitHub archive still verifies while any content change aborts the install. The
loader re-checks the hashes before every import. To move the pin: fetch the new commit, hash
those four files, update `UPSTREAM_SHA` and `UPSTREAM_FILES` together, and re-run the tests.

The code imports as a top-level package literally named `model`; the loader puts the pinned
checkout first on `sys.path` and refuses to run if `import model` resolves anywhere else.

## Inference guards the upstream examples lack

- `tokenizer.eval()` and `model.eval()` after loading: with `huggingface_hub < 2` the mixin
  returns modules in training mode (dropout on), which made results differ across
  environments (issue #415).
- `top_k=0` always: upstream silently ignores `top_p` when `top_k > 0`.
- Offline loading (`HF_HUB_OFFLINE=1`) from the local snapshot directories.
- Uncertainty band: K copies of the series with `sample_count=1` give K independent paths;
  `predict()` alone returns only their mean. The backtest uses the mean of `--samples` paths.
- One forecast per process and few batched calls per backtest (issue #403: `predict()` hangs
  after ~20–40 calls in one process on Windows).
- Future timestamps are generated by the skill (weekdays, 24x7 or replayed intraday
  sessions); the model only sees their calendar features.

## Resource estimates (CPU, 4 vCPU, est. from parameter counts — measure on your host)

| | mini | small | base |
|---|---|---|---|
| Peak RAM incl. torch + pandas | ~0.6 GB | ~0.8–1 GB | ~1.5 GB |
| Time per sampled path, 400-bar context, 30 steps | ~1–4 s | ~6–20 s | ~30–80 s |

Cost scales roughly linearly with horizon, context and samples because the decoder has no KV
cache and re-runs the whole window every step. CPU-only torch from the PyTorch CPU index is
~200 MB to download (~1 GB installed); the default PyPI wheel on Linux pulls 3–5 GB of CUDA
libraries, which is why setup installs torch in a separate step from that index.

## CPU knobs (`kronos_forecast.py` / `kronos_backtest.py`)

| Knob | Default | Effect on a CPU-only VPS |
|---|---|---|
| `--model` | `small` | `mini` ≈ 5x faster, context 2048; `base` ≈ 4x slower |
| `--lookback` | 400 (backtest 256) | bars of context; cost grows linearly (max 512, mini 2048) |
| `--horizon` | 10 (backtest 5) | candles ahead; cost and error grow with distance |
| `--samples` | 8 (backtest 4) | sampled paths for the band; cost grows linearly |
| `--threads` | all cores | cap it when the VPS also serves the gateway |
| `--calendar` | `auto` | `nyse` (holidays, early closes; what `auto` picks without weekend bars), `24x7` (crypto), `weekdays`/`sessions` (no exchange holidays) |
| `--timeout` | 1800 s | abort a run that takes longer |

A scheduled routine over a watchlist runs one forecast per symbol (about a minute each on
4 vCPU with the defaults); for long watchlists or hourly schedules use `--model mini` or
`--samples 4`, and `--threads 2` when the gateway shares the machine.

## Known independent evaluations

- Issue #354: Kronos-mini zero-shot on AAPL daily, 1,800 forecasts — MAPE 12–22% worse than
  persistence in every configuration; direction accuracy ~48–54%.
- Issue #375: Kronos-small on 182 US equities after the pretraining cutoff — cross-sectional IC
  +0.022 (not significant); 90% sampled bands covered 58% of outcomes (~2.7x too narrow).
- Issue #415: training-mode loading (fixed here with `.eval()`); even in eval mode the
  reporter's AAPL intervals lost to a random walk with an EWMA band.

These are why `kronos_backtest.py` exists and why the procedure runs it before presenting a
forecast as useful.

## Baselines in the backtest

`kronos_backtest.py` scores every origin against two baselines fitted on the same window:
"repeat the last close" and exponential smoothing on the closes. The ETS forecast comes from
statsforecast's `AutoETS(season_length=1)` (Apache-2.0, picks the error/trend form by AICc) when
`kronos_setup.py` could install it, else from a built-in additive Holt fit (simple smoothing or a
damped trend, grid-searched on one-step error); the output names the engine. `adds_value`
requires a 2%+ lower MAE than both and a direction hit rate of at least 50%, so the verdict is
never looser than the old naive-only rule, and automatic buys need it (learning-loop.md).
